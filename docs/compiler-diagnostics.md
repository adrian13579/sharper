# Compiler and policy diagnostics

`sharplint check` returns C# compiler diagnostics and SharpLint policy findings
for the same validated Roslyn solution. Compiler errors do not stop Naming or
other syntax policies. Both daemon checks and `--no-daemon` use
`WorkspaceCoordinator`; the latter starts from a fresh workspace and cache.
SharpLint never applies code fixes or writes target source files.

## Collection and output

For directories containing C# projects, the coordinator loads the recursive
`.csproj` files and their project references through `MSBuildWorkspace`, using
the installed SDK selected by MSBuild. Restore the projects before checking.
Project-load failures, including missing restore assets, fail analysis explicitly.
There is no `dotnet build` or restore subprocess on every check. Workspace loading
uses MSBuild's design-time targets to obtain compiler inputs; this can produce
SDK intermediate files in `obj`. As with executable SharpLint configuration,
project targets must be trusted: arbitrary custom targets are not sandboxed.

The host calls `Project.GetCompilationAsync` and `Compilation.GetDiagnostics`.
It retains Roslyn IDs (`CS0103`, `CS0246`, etc.), invariant-culture messages,
effective severity, and source locations. Project warning levels, `NoWarn`,
warning promotion and suppression remain compiler decisions. Hidden and suppressed
compiler diagnostics are omitted. Analyzer references discovered in target projects and source
generators are **not automatically executed**; those references are removed from
the captured solution before compilation. External analyzers explicitly registered
through SharpLint configuration run separately as module policies against the
project compilations. See [module contracts](spec/taxonomy.md). Already materialized generated Compile inputs are
included and tracked. Policies continue to exclude `bin`/`obj` sources. Types supplied only by an unexecuted generator may therefore
produce compiler errors. Build validation is required for generator-dependent code.

When no `.csproj` exists, ordinary C# files form one synthetic library using the
running .NET framework assemblies and Roslyn's default language/warning options.
This provides useful compiler feedback for snippets but cannot infer package
references, executable output, defines, or intended target frameworks. Add a real
project for project-accurate diagnostics. With real projects, excluded/unowned
source files remain syntax-policy inputs and are not compiled as a second program.
The executable `sharplint.config.cs` remains policy input and is excluded from
target-program compilation, even if the project's default glob includes it.

The existing JSON diagnostic fields remain available. Additions are `origin`
(`compiler` or `sharplint`), `project`, `helpUrl`, `spanStart`, and `spanLength`.
Compiler categories come from their descriptors (normally `Compiler`); Naming
retains `naming` and its existing `naming.*` IDs. `ruleId` carries compiler IDs
as well as policy IDs. Example diagnostic objects:

```json
[
  {
    "ruleId": "CS0103", "origin": "compiler", "category": "Compiler",
    "severity": "error", "message": "The name 'missing' does not exist in the current context",
    "file": "/repo/App.cs", "line": 1, "column": 26,
    "project": "/repo/App.csproj::App", "spanStart": 25, "spanLength": 7
  },
  {
    "ruleId": "naming.class.prefix", "origin": "sharplint", "category": "naming",
    "severity": "error", "message": "Class 'Wrong' must start with 'Expected'.",
    "file": "/repo/App.cs", "line": 1, "column": 7,
    "project": "/repo/App.csproj::App", "spanStart": null, "spanLength": null
  }
]
```

JSON coordinates are **one-based physical lines and UTF-16 columns**; `#line`
mapping does not change them. Compiler spans are zero-based UTF-16 offsets and
lengths in that physical source. Diagnostics without file locations have null
`file`, `line`, `column`, and spans. Core represents this using
`HasSourceLocation = false` and a default `SourceLocation`. Project identity is
the project path plus Roslyn's project name, retaining target contexts rather
than merging linked-file findings across projects.

Aggregation removes exact duplicate records and sorts by normalized path,
line/column, project, origin, ID, severity, message and remaining metadata.
Neither project IDs generated by Roslyn nor worker completion order affect output.
The top-level `status` is `completed` or `incomplete`; `failures` identifies rules
whose prerequisites could not be satisfied. Snapshot information remains under
the optional `--stats` statistics object. Pretty output labels each origin:

```text
error CS0103 [Compiler]
  The name 'missing' does not exist in the current context
  /repo/App.cs:1:26
  project: /repo/App.csproj::App
error naming.class.prefix [SharpLint]
  Class 'Wrong' must start with 'Expected'.
  /repo/App.cs:1:7
```

Exit 0 means completed analysis without errors; warnings/info are nonblocking.
Exit 1 means compiler or policy errors. Project `TreatWarningsAsErrors` or
`WarningsAsErrors` makes selected compiler warnings blocking; Naming uses
`.AsError()`. Exit 2 means incomplete analysis, configuration failure, or analysis
infrastructure failure. Exit 3 retains the existing daemon communication contract.
Ordinary C# errors are diagnostics, never infrastructure failures.

## Incremental validity

The coordinator keeps one current immutable solution, a Naming result per live
document context, and compiler results per project. Unchanged checks reuse
compiler groups without calling `GetDiagnostics` again. The same serialized
request gate deduplicates concurrent equivalent analysis work. Source edits
update every owning Roslyn document, including linked documents. Compiler groups
for all owning projects and their transitive dependents are invalidated using
`ProjectDependencyGraph`; unrelated groups remain cached. Naming retains its
document cache. Unknown custom-module dependencies still execute over the complete
input snapshot on every check, with project compilations supplied to Roslyn analyzers.

Source membership changes or compilation-metadata changes reload the workspace
conservatively. Captures hash project files, imported props/targets (including
external imports), project assets, additional/analyzer configuration inputs,
reference binaries, external compiler rulesets and their nested includes, signing
key inputs, and materialized `obj` C#/JSON/build inputs. Referenced
projects outside the root and their source trees are reconciled too. Optional
imports and custom import globs are tracked so creation/removal invalidates the
capture. Multi-target imports are evaluated for each declared target framework.
Newly discovered dependencies require a retry with a pre-load capture; a post-load
observation alone cannot validate the options that were already loaded.

References are captured as immutable metadata images on reload, preventing Roslyn
file-reference caches from concealing same-path binary changes. Content hashes,
not timestamps alone, establish validity. Before publication, a second input
capture and the watcher epoch must agree. Failed, unstable or canceled attempts
keep the last published solution/cache but never return that old result as a
successful new check. Superseded workspaces are disposed. The existing
[snapshot trust boundary](daemon.md#consistency-and-trust-contract) still applies:
two equal observations cannot prevent an external writer from changing files
immediately afterward or changing and restoring them between observations.

`--stats` includes `projectsInWorkspace`, `projectsAnalyzed`, `projectsReused`,
`compilerDiagnostics`, and `sharpLintDiagnostics`, alongside document hit counts
and existing timings. Phase timings cover the published attempt; CLI elapsed time
also includes dependency-discovery retries. Project counts exclude the syntax-only auxiliary project.
Document counts describe Roslyn document contexts, so linked files can count more
than once; `filesAnalyzed` counts distinct captured source paths, including config
and materialized generated inputs.

## Future policies and build limitations

`RuleDefinition.InputRequirement` defaults to `Syntax`. A module may declare
`ErrorFreeCompilation`; when compiler errors exist, or the host cannot validate
that prerequisite, the module is not invoked and an explicit `AnalysisFailure`
makes the result incomplete. Compiler and safely executed policy findings remain
in the response. Hidden policies do not require execution. A standalone Core
syntax host leaves `CompilationHasErrors` unset and therefore cannot claim to
satisfy a compilation prerequisite. The coordinator supplies project compilations to module policies and configured
Roslyn analyzers. Built-in Architecture and explicit-boxing policies use semantic
models and require a validated error-free compilation. Analyzer exceptions continue to fail analysis explicitly.

Roslyn diagnostics are not equivalent to `dotnet build`: custom targets, emit-only
errors, generators, analyzer packages and artifacts not supplied by design-time
loading may need a separate build. Solution configuration mappings are not selected:
the root's recursive C# projects are loaded using their default configuration.
Roslyn 5.3 matches the repository's .NET 10 compiler generation. Its bundled
version determines supported language features, independently
of the installed SDK. A change to the selected SDK fails explicitly and requires a daemon restart,
because in-process MSBuild registration cannot switch SDKs. Environment changes, arbitrary MSBuild property
functions and external executable-config dependencies need a fresh process or
`--no-daemon`; inputs derived from time/network/process state are not made pure by
content hashing. No full build pipeline, source rewriting, or automatic fixes are
part of this feature.

Regression tests are in `Daemon/CompilerDiagnosticsTests.cs`,
`Daemon/WorkspaceCoordinatorTests.cs`, `Analysis/TaxonomyAnalyzerTests.cs`, and
`Cli/CompilerFunctionalTests.cs`. Differential comparisons use fresh complete
coordinators and daemonless CLI checks and compare full diagnostic records/JSON,
including origin, ID, category, severity, message, project, locations and spans.

Source capture decodes UTF-8 with BOM detection. Legacy code-page overrides are
not modeled; validate those projects with their compiler build separately.
